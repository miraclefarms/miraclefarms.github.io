当 LongBench v2 的论文出现在 arXiv 时，长上下文评测领域有了一个值得认真对待的新坐标。不是因为它规模最大，而是因为它做了一件更根本的事：把「深度理解与推理」而不是「大海捞针」变成了评测的核心维度。

这个区别看起来微小，实际上划出了两种benchmark的分水岭。前者问的是「模型能不能找到信息」，后者问的是「模型能不能真正理解信息并据此推理」。LongBench v2 的设计正是围绕后一个问题展开的。

## 一、benchmark 设计：为什么要用选择题、为什么要让人来标定难度

LongBench v2 包含 503 道多选题，上下文长度从 8K 到 2M token，横跨六个任务类别：单文档 QA、多文档 QA、长上下文 in-context learning、长对话历史理解、代码仓库理解和长结构化数据理解<a href="https://arxiv.org/abs/2412.15204">[1]</a>。

这个设计有几点值得展开讨论。

**多选题格式不只是为了自动评分**。在开放式长问答中，评分本身的可靠性是瓶颈——即使引入人工评估，也很难保证不同标注者之间的一致性。多选题让评测精度有了确定性保障，但代价是需要解决一个难题：什么样的多选题才能真正测出深度理解，而不是恰好在文本里藏了一个可以用浅层匹配解决的问题？

LongBench v2 的解法是大规模引入人工标注。他们召集了将近 100 位来自不同专业背景的高学历人士，基于真实文档构造问题，并经过自动化审查和人工审查两道关卡。数据通过审查才能获得标注奖励——这个机制本身保证了题目不是trivial的。

![LongBench v2 数据采集流程](/assets/longbench-v2/fig-5-pipeline.png)

*图 1：LongBench v2 的数据采集 pipeline。标注者上传文档并提出多选题后，系统会经过自动化和人工双重审查，只有通过所有审查阶段的数据才能获得奖励。来源：论文原图。*

**人工基准不是可选的，而是理解难度的锚**。最终人类专家在 15 分钟时间限制下的准确率只有 53.7%。这个数字本身非常重要：即使给人类专家配备文档搜索工具，让他们自由检索，他们仍然有 46.3% 的概率答错。这意味着 LongBench v2 的题目确实达到了需要深度推理才能解决的难度层级，而不是普通阅读理解。

![各任务类别长度分布与专家解题时间](/assets/longbench-v2/fig-1-length-dist.png)

*图 2：（左）各任务类别的长度分布，涵盖从短文本到超长文本的场景；（右）人类专家解答时间分布，约一半题目需要超过 15 分钟才能给出正确答案。来源：论文原图。*

## 二、六大任务域：各自的挑战本质是什么

LongBench v2 的六个任务类别不是随便拼凑的，而是对应了长上下文在真实场景中的六种主要用法。

**单文档 QA** 是最基础的设定：给定一篇长文档，回答基于全文理解的问题。这里的难度在于，全文理解要求模型在极长上下文内保持信息一致性，不能遗漏关键细节也不能被无关内容带偏。

**多文档 QA** 引入了信息分散的挑战——答案可能分布在多篇文档的不同位置，需要模型具备跨文档的信息聚合与推理能力。

**长 in-context learning** 考核的是模型在超长上下文示例中提取模式的能力。Few-shot 在短上下文有效，但在极长上下文下，示例中的模式信号会被稀释，模型能否仍然有效利用示例信息是这里的核心问题。

**长对话历史理解** 模拟的是多轮交互场景。对话历史本身包含大量冗余、重复和噪声，模型需要在其中追踪关键意图、实体和时序关系。这与 agent 场景的关联最为紧密。

**代码仓库理解** 要求模型在完整的代码库上下文（包括多个文件的依赖关系、调用图、全局变量）中完成代码理解任务。这对于代码 agent 和代码辅助工具非常重要。

**长结构化数据理解** 针对的是表格、JSON 等结构化输入的深度理解，考验模型在结构与文本混合场景下的推理能力。

![各任务域的详细统计信息](/assets/longbench-v2/fig-2-task-stats.png)

*图 3：LongBench v2 六个任务域的具体统计，包括数据量、中位长度、专家准确率和专家解题时间中位数。来源：论文原图。*

从这些数字可以读出一个规律：代码仓库理解和长对话历史理解是难度最高、专家时间消耗最长的两个类别；而单文档 QA 在 easy 子集上人类可以达到接近 100% 的准确率，但 hard 子集则显著更难。

## 三、核心发现：最强模型直接作答只有 50.1%，推理链让 o1-preview 超越人类

这是 LongBench v2 最值得记住的一组对比数据。

当 16 个主流模型直接回答问题时，表现最好的是 Gemini-Exp-1206（2024年12月6日版本），达到 **50.1%** 准确率——刚好和人类专家在 15 分钟约束下的 53.7% 持平，但还未超越。这个数字本身就是一种标定：在 LongBench v2 的难度下，没有任何不经推理增强的模型能可靠地超过人类。

但 o1-preview 的出现改变了这个格局。o1-preview 在同样条件下取得 **57.7%**，比最强直接作答模型高出 7.6 个百分点，也比人类专家的 53.7% 高出 4 个百分点<a href="https://arxiv.org/abs/2412.15204">[1]</a>。

![各模型在各任务域的雷达图对比](/assets/longbench-v2/fig-3-radar.png)

*图 4：各模型在六个任务域上的平均得分（按最高得分归一化）。雷达图直观显示了 o1-preview（标记为 🧠 的推理模型）在各维度上的全面领先。来源：论文原图。*

这带来了一个清晰的信号：**推理时计算扩展（inference-time compute scaling）是攻克长上下文深度理解问题的有效路径**。这不是简单的「用更大的模型」或「用更长的上下文窗口」，而是在推理阶段引入更长的 chain-of-thought，让模型有机会在回答前进行多步推理和验证。

这个结论与 2024 年下半年以来推理模型（reasoning models）逐渐成为主流的过程是吻合的。LongBench v2 提供了迄今为止最系统的实验证据，证明在长上下文场景下，inference-time compute 的投入确实能带来能力边界的扩展。

## 四、+RAG 实验：长上下文不一定是必选项

除了直接评测，LongBench v2 还做了 +RAG 评测：用 retrieval 从上下文里抽取 top-N chunk 再送入模型，观察不同 retrieval 深度下的性能变化。

![RAG 评测结果：不同 context length 下的性能曲线](/assets/longbench-v2/fig-4-rag-curve.png)

*图 5：RAG 模式下，将 top-4、8、16、32、64、128、256 个 512-token chunk 作为上下文时，各模型的性能曲线。显示在足够召回相关 chunk 时，较短上下文可以达到与全文档相当的效果。来源：论文原图。*

实验结果揭示了一个对系统设计非常重要的结论：当 retrieval 足够精准时，用较短上下文 + RAG 的方式可以达到与全文档上下文相当的效果。换句话说，**上下文长度不是越长越好，关键是召回的相关信息是否充分**。

这对推理系统的工程设计有直接影响：与其把所有 token 都塞进 context window，不如在 retrieval 质量上投入更多资源。LongBench v2 的 +RAG 实验表明，当 top-64 到 top-128 chunk 都能有效召回时，性能就已经趋于饱和，继续增加召回量边际收益有限。

## 五、Leaderboard 的分层信号

从 LongBench v2 的 leaderboard 可以读出更细致的分层现象。

**推理模型与非推理模型的差距在 Easy/Hard 子集上表现不同**。在 Easy 子集上，非推理模型（GPT-4o 等）可以达到 50% 左右的准确率，推理模型的领先幅度相对有限。但在 Hard 子集上，推理模型的优势显著扩大，部分原因是 Hard 子集的问题通常需要多步推理而非直接检索。

**上下文长度与 Easy/Hard 子集没有简单的负相关**。这是因为不同长度范围的 task 分布差异很大：Long 子集包含的更多是多文档和代码仓库类任务，这些任务本身对模型能力的要求就更高，并不单纯因为「更长」而更难。

**Qwen3 系列引人注目**。Qwen3-235B-A22B 在 non-thinking 模式下达到 46.7%，但在 thinking 模式（16K token thinking budget）下达到 60.6%——提升了近 14 个百分点。这个差距是目前为止同模型不同配置下最大的提升幅度之一，说明 thinking budget 对 Qwen3 的能力释放非常重要。

## 六、为什么这个 benchmark 值得关注

LongBench v2 不是又一个「刷榜」型 benchmark。它之所以值得认真对待，有三个原因。

**第一，它锚定了人类能力边界**。之前的 LongBench、BasketBench 等工作都缺少严格的人工基准，导致「模型已经超过人类」的宣称缺乏可信参照。LongBench v2 的 53.7% 人类准确率提供了一个可信的锚，让模型超越人类的结论有据可查。

**第二，它把评测维度从「大海捞针」推进到了「深度推理」**。大海捞针考察的是模型在长上下文中检索信息的能力，这在实际应用中当然有用，但它不测模型是否真正理解信息并基于此推理。LongBench v2 的题目需要模型在全文理解基础上进行推理，这让评测更贴近真实应用需求。

**第三，它为推理时计算扩展提供了系统化的实验平台**。o1-preview 的成功不是偶然的——LongBench v2 的实验设计让它可以在同一个 benchmark 上比较推理和非推理模型、比较不同 thinking budget 设置、比较 +RAG 和全上下文两种策略。这意味着未来任何声称在长上下文推理上有突破的工作，都必须在这个 benchmark 上给出可信的数字。

## 七、结论

LongBench v2 的出现把长上下文评测从「窗口够不够大」的硬件问题，变成了「推理够不够深」的能力问题。这个转变对 AI Infra 的影响是直接的：当模型的瓶颈从显存容量转向推理链路设计时，系统架构的重点也需要相应调整——比如在 memory 层面支持更长的 KV cache 生命周期，在调度层面支持推理时的动态计算分配，在 retrieval 层面提升召回精度以减少不必要的上下文负载。

从更大角度看，LongBench v2 验证了一个趋势：LLM 在长上下文上的进展，不会只靠把 context window 做到 1M 或 2M 来完成；推理时计算的扩展，可能是下一阶段能力提升的主要杠杆。这个判断对训练基础设施和推理系统设计的方向都有影响。

当前模型在 LongBench v2 上的最优成绩是 57.7%（o1-preview），离人类专家还有约 3 个百分点的空间。但考虑到 reasoning model 的迭代速度，这个 gap 的弥合可能不会太久。
