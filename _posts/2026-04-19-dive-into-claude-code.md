如果你打开 Claude Code 的源码，你会发现它的核心是一个 while 循环：调用模型、执行工具、拿回结果、循环往复。这个循环本身只有几十行，但围绕它的系统——权限管理、上下文压缩、工具路由、安全拦截——才是真正的工程复杂度所在。

VILA Lab 最近发布的论文《Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems》<a href="https://arxiv.org/abs/2604.14228">[1]</a>，系统地对这套架构做了源码级的逆向分析。论文的核心发现直接颠覆了人们对"AI 编程工具"的直觉认知：Claude Code 的 JS 运行时基础设施只占整个代码库的 **1.6%**，剩余 **98.4%** 是纯文本——prompt、markdown 文档、配置文件。换句话说，这个系统绝大多数的"逻辑"，写在了给模型看的语言里，而不是传统意义上的代码里。

这不是一个编程风格的选择，而是一个哲学立场：**把判断权交给模型，基础设施只负责保证判断被安全地执行**。

## 一、五个价值观，十三条原则

论文从 Claude Code 的实现中提炼出五个驱动架构决策的核心价值观：人类决策权威（human decision authority）、安全与安保（safety and security）、可靠执行（reliable execution）、能力放大（capability amplification）和上下文适应性（contextual adaptability）。这五个价值观不是口号，它们被追溯到 13 条具体的设计原则，再往下落实到一个个可观察的实现选择。

这种分析框架本身就值得关注。通常我们谈论一个系统的架构，讨论的是模块划分、接口设计、数据流向。VILA Lab 的分析把层次拉得更高：先问这个系统的**价值立场**是什么，再问它如何在技术选择中体现。这种逆向工程的方式，揭示了一个有意思的结论——Claude Code 的每一个看似"简单"的设计，背后都有一条可以追溯到价值观的线索。

以"minimal footprint"原则为例。Claude Code 的设计目标是：在完成任务所必需的范围内，尽可能少地占据用户系统资源、尽可能少地积累状态。这体现在会话存储是追加式的 JSONL 文件而不是数据库、subagent 在独立 worktree 中执行而不是在主进程中运行、工具调用的结果直接喂回循环而不是缓存在中间层。简洁不是偷懒，而是一种对"能做的边界"的刻意克制。

## 二、54 个工具，9 步流水线

在实现层面，Claude Code 内置了最多 **54 个工具**，覆盖文件操作、搜索、Shell 执行、网络访问和代码智能等五大类别。工具池的组装遵循一个 5 步流程：基础枚举（最多 54 个工具）→ 模式过滤 → 拒绝列表预筛 → MCP 整合 → 去重。这个组装过程决定了 Claude 在每次会话中实际能用什么——不是所有工具都默认可用，而是根据当前模式和权限配置动态生成。

每一轮对话的执行遵循一条 9 步流水线：设置解析 → 状态初始化 → 上下文组装 → 5 个 pre-model shaper → 模型调用 → 工具分发 → 权限门控 → 工具执行 → 停止条件判断。这里有一个关键的设计哲学：**模型决定要做什么，权限系统决定是否允许做**。两者是完全独立的代码路径，因此一个被越狱的模型也无法绕过基础设施层面的安全检查——因为它们根本不在同一个执行链条上。

**27 个 hook 事件**分布在这条流水线的关键节点，覆盖 5 个类别，支持 4 种执行类型（shell 命令、LLM 评估、webhook 回调、subagent 验证器）。这个设计给用户提供了在不修改 Claude Code 本身的前提下注入自定义逻辑的能力——安全校验、日志采集、行为审计，都可以通过 hook 而不是 fork 来实现。

## 三、上下文是最稀缺的资源

Claude Code 对上下文管理的重视程度，在系统架构上体现得非常明显。论文描述了一套 5 层上下文压缩（compaction）机制：当上下文接近窗口上限时，系统首先清除旧的工具输出，然后触发一次完整的 LLM 摘要，生成一个包含 9 个结构化章节的会话摘要，再用这个摘要加上最近的文件内容（上限 50K token）、技能定义、工具列表和 CLAUDE.md 指令重建上下文。这个压缩过程设置了一个"边界标记"，让模型知道哪些是摘要后重建的内容，哪些是真实的近期上下文。

这套机制带来的一个关键数字是 **92% 的前缀复用率**——系统提示、工具描述等静态内容在多轮调用中被缓存复用，只有动态上下文（当前任务状态、最近交互）每轮重新构建。这意味着多轮对话的 token 消耗不会线性增长，而是保持相对稳定的基础成本加上动态增量。

CLAUDE.md 在这里扮演了一个关键的接口角色：它是用户唯一可以直接干预上下文压缩结果的机制。在 CLAUDE.md 中写入 `Compact Instructions` 章节，可以告诉压缩系统在摘要时重点保留哪些信息。这个设计把"会话记忆的持久化"问题，从代码层面推给了用户配置层面——符合"minimal footprint + 用户掌控"的一贯逻辑。

## 四、与 OpenClaw 的六维对比

论文把 Claude Code 的架构与 OpenClaw——一个独立的开源 AI agent 系统——做了六个维度的对比：权限模型、上下文管理、工具整合、透明度、可扩展性、对话连续性。

两者的核心差异体现在部署上下文的不同。Claude Code 是面向单一用户的终端工具，因此它的权限模型是**逐动作分类**的：每次工具调用都经过一个 ML 分类器判断风险等级，7 种权限模式覆盖从完全手动审批到自动执行的整个光谱。OpenClaw 面向的是多租户网关场景，权限模型转向**外围访问控制**：在 agent 进入系统时就做资质验证，而不是在每次动作时介入。

同样的问题，因为部署上下文不同，就产生了完全不同的技术答案。这正是论文想要指出的核心论点：**没有普适的 agent 架构，只有在特定约束下最合理的架构**。Claude Code 的 while 循环在单用户终端场景下足够简洁有效；如果要把同样的设计搬到企业级多租户环境，它的每一个假设都需要重新检验。

## 五、结论

Claude Code 的 1.6%/98.4% 这个数字，可以用两种方式解读。悲观的解读是：这个系统把大量的逻辑外包给了语言模型，缺乏传统工程意义上的可预测性和可调试性。乐观的解读是：这个系统找到了一种让模型判断力最大化发挥的结构，而不是用代码去过度约束它。

VILA Lab 的分析倾向于后者，但也给出了边界条件：这套哲学成立的前提，是模型的判断力足够可靠，以及基础设施层面的安全机制足够健壮。当模型能力提升时，可以进一步减少基础设施的干预；当任务风险增加时，权限系统和 hook 机制提供了干预的接口。这是一个**可调节的信任光谱**，而不是无条件地把一切交给模型。

对于今天正在构建 agentic 系统的工程师来说，这篇论文的价值不在于告诉你怎么复制 Claude Code，而在于把架构决策背后的逻辑链条显式化：先问你的系统服务于什么样的用户、在什么样的部署环境中运行，再问哪种权限模型、哪种上下文管理策略、哪种工具路由机制是合理的。方法论本身，比任何一个具体的架构选择都更值得带走。
