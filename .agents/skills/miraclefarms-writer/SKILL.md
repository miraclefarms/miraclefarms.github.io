# MiracleFarms Writer

给定主题 + 参考链接 -> 自动调研 -> 产出可直接发布到 miraclefarms.github.io 的 `_posts/` 文章。也可对已有文章进行修改润色。

如果参考资料里出现论文 figure、官方博客架构图、GitHub README / PR 截图等可帮助理解正文的图片，额外读取 `references/image-handling.md`，按其中的原图优先与回退策略处理。
如果用户要求微信公众号版本，额外读取 `references/wechat-format.md`，按其中的渠道改写与参考资料链接保留规则处理。

**重要分叉：**
- `brief -> 微信公众号` 与 `essay -> 微信公众号技术长文` 可以复用大部分调研与素材整理路径，但**走不同的格式与发布路径**。
- `essay -> 微信公众号技术长文` 与 brief 可以复用大部分路径，但**配图和配色必须单独处理**，不能沿用日报默认值。
- `essay 改写成微信公众号技术长文` 时，必须显式走长文路径：保留与 GitHub.io essay 同一组正文配图、写入 `wechat_variant: essay-longform`、并使用技术长文的经典蓝主题。
- 不要把 essay 的微信公众号版本退化成只有题图、无正文配图的日报模板；这会让写作规范和发布脚本产生不一致。

## 第一步：判断文章类型

在开始调研之前，先确认写哪种文章：

**Essay（技术深度分析）**
- 主题是深度技术分析、架构分析、源码解读、benchmark 综述，有完整的核心论点
- 通常 800–3000 字，结构严密
- 作者：Lychee & Ethan

**Reading（论文阅读 / 技术综述）**
- 主题是对单篇论文或单一技术主题的阅读笔记、解读或综述
- 结构与 Essay 一致（HTML anchor 引用、`## 参考资料`），但声音是**带立场的阅读笔记**——不是中立地复述论文，而是以质疑者和翻译者视角审视：这个工作在生产里成不成立？它的真正贡献是什么？边界在哪里？
- 允许更多"站在 X 角度看""这篇论文最值得被记住的地方是……"这类显式视角切换
- 作者：Ethan

**Brief（日报 / 简报）**
- 主题覆盖多个项目过去 24–48 小时的更新进展
- 或用户明确说"日报/简报/brief"
- 作者：荔枝不耐思

**如果用户没有明确说明类型**，根据参考资料判断：
- 参考资料以 PR 列表为主 -> brief
- 参考资料是一篇论文 / 单一技术主题 -> reading（偏解读）或 essay（有明确原创判断）
- 仍不确定 -> 直接问用户

**文章修改润色**：如果用户提供了已有文章（本地路径或粘贴全文），而不是主题+链接：
- 直接读取用户提供的文章内容和参考链接
- 应用同样的写作原则（开篇立旗、叙述为主、避免 AI 味句式）
- 保留原有 front matter，只修改 body 内容
- 如用户未提供新参考资料，跳过调研步骤，直接进入写作原则检查与修改

## 第二步：调研

**对每个提供的参考 URL：**

- **GitHub PR**：读取 PR 标题、description、comment、changed files（重点看 diff 摘要）。提取：做了什么、解决了什么问题、影响了哪个模块。
- **arXiv 论文**：读取摘要、Introduction、核心贡献段落、实验结论。重点提取：核心创新是什么、和现有工作的差异、关键数字结论。
- **博客 / 官方文档**：读取全文，提炼核心观点和数据。
- **本地 _posts/ 文章**：直接 read 文件，作为背景参考。

**同时提取候选图片**（如果有）：

- 记录图片 URL、所在段落 / figure caption、它支持的是哪一个论点。
- 只保留和核心判断直接相关、能帮助读者理解机制 / 架构 / 实验结果的图。
- 忽略 logo、作者头像、装饰性 banner、营销海报、与正文无关的界面截图。
- 优先保留原始来源中的 caption 或上下文说明，后面写图注时要用得上。

**证据可信度优先级**（影响你可以做多强的判断）：
1. 论文原文（arXiv / conference）
2. 官方 PR / commit（已合并）
3. 官方 Release / 官方博客
4. 官方文档（README / API docs）
5. 新闻报道 / 二手转述

**确定核心判断**：在写作之前，先问自己——"这批材料最想说明什么？有没有一个能贯穿全文的核心观点？"这个判断是文章的骨架，不是材料的汇总。

如果参考资料不足以支撑某个具体判断，要在文中标注"尚待验证"或"基于推断"。

## 第三步：声音与视角

你的声音是一个**在一线碰过这些系统的人**，在跟同样关心这些系统的人聊天。不是教授讲课，不是记者报道，不是布道师传教。

写作时可以在以下视角之间自然切换，一篇文章里用 2-3 种即可：

| 视角 | 做什么 | 例句 |
|------|--------|------|
| 拆解者 | 分享发现过程，带读者一起看结构 | “理解了硬约束，再看 Claude Code 的提示词架构就能看出每个细节为什么这样写。” |
| 翻译者 | 把行话换成直觉能接住的说法 | “用户只是多问了一句，系统背后却要决定，是重新读完整本书，还是接着手里已有的笔记往下写。” |
| 连线者 | 串联散落的事实，让趋势浮出水面 | “同一天内有四个独立项目各自突破了非 NVIDIA / 非 x86 的部署路径，这不是巧合。” |
| 质疑者 | 替读者问出边界问题 | “但这个结论有一个前提……””论文没有回答的是……” |
| 考古者 | 追溯设计决策的来历，用历史细节建立可信度 | “这个数字不是理论最佳，是真实成本倒逼的工程决策。” |

**不要**固定在某一个视角上写完全文。自然切换本身就是层次感。

### 不同文章类型的声音倾向

- **Brief**：连线者为主（串联当天多条进展）+ 质疑者（点出趋势判断的边界）
- **Essay**：拆解者为主（带读者一层层深入）+ 考古者（用生产细节和历史数据建立判断）
- **Reading**：质疑者为主（带立场地审视论文，替读者问出”这在生产里成不成立”）+ 翻译者（把论文语言转化为工程直觉）

## 第四步：写作原则（Brief / Essay 通用）

### 开篇即核心判断

文章第一段必须是核心判断或核心问题。”X 项目最近发布了 Y”是背景介绍，”这波更新说明推理框架正在进入质量竞争期”才是值得开篇的东西。读者读完第一段就应该知道这篇文章最想说什么。

开篇要**具体**：用一个能让读者感受到问题存在感的场景或数字切入，而不是抽象地宣布”X 很重要”。

- ❌ “KV cache 管理是推理系统中的重要问题。”
- ✅ “一次普通的 chat 调用可能 2K token、单轮就结束；一次 Claude Code 任务可能跑 50 次模型调用，每次都背着 30K 以上的固定开销。”

### 叙述为主，不用列表

关键概念用段落展开，用”因此 / 但是 / 同时 / 由此”等过渡语连接。避免把三个 PR 变成三个 bullet。并列事实组织成有逻辑递进的叙述——“首先……其次……最后……”作为固定段落公式偶尔可以，但不能每节都这样起头，那是行文节奏机械的信号。

### 每个技术段落都要回答”so what”

写完一段技术事实后，问自己：这对读者意味着什么？然后用一句话把这个含义写出来。没有 so what 的段落读起来像文档，有 so what 的段落读起来像洞察。

- ❌ “缓存匹配是 prefix 字节级的精确匹配。”（结束）
- ✅ “缓存匹配是 prefix 字节级的精确匹配——任何字符变动都会换一条 prefix。这套层级是 Claude Code 七种优化模式里大多数决策的物理前提。”

### 用具体数字锚定判断

核心判断至少附带一个量化证据。没有数字的判断听起来像意见，有数字的判断听起来像洞察。数字不需要堆砌——一个精准的数字比三个模糊的形容词更有冲击力。

- ❌ “cache 命中能显著降低成本。”
- ✅ “cache read 是 0.30 美元/MTok，未命中是 3 美元/MTok，差 10 倍。”

数字来源必须可追溯：论文实验数据、PR 描述里的 benchmark、官方定价页面。不要编造或推测具体数字。

### 复杂概念用类比降维

当一个概念第一次出现且对非专业读者有门槛时，考虑用一个日常场景做类比。好的类比让读者跨越认知门槛后就不再需要；不要每段都用类比，一篇文章里 1-2 处足够。

- ✅ “第一轮请求像是把一整本书交给模型读，prefill 节点读完后把笔记交给 decode 节点写回答。”
- ✅ “PagedAttention 把内存管理问题从'找一整块连续空地'变成了'按页分配'，思路和操作系统的虚拟内存一脉相承。”

### Bold 加粗策略（Brief 为主）

Brief 里每个 H2 章节最多 1-2 处 bold，用于标记**该节的核心判断句**。Bold 不用于强调名词或修饰语，而是标记那句”如果读者只看一句话，应该看到哪句”。

- ✅ **把 DeepSeek 全系列的推理性能当作一条独立产品线来推进**
- ❌ **TRT-LLM** 合并了多个 PR（名词加粗没有信息增量）

Essay 和 Reading 一般不用 bold，靠段落结构和句式本身传递重点。

### 配图必须服务论点

- 只插入真正帮助理解正文判断的图，不追求”有图就放”。
- 图片应尽量放在第一次深入分析该机制 / 实验 / 架构的位置附近，而不是统一堆到文末。
- 图注要说明”这张图说明了什么”，不是只复述文件名或来源标题。
- 如果某张图抓取失败且存在替代图，优先换图；如果没有替代图，不要为了凑图而削弱文章质量。

### 有观点，有边界

- 允许第一人称判断：”这里有一个值得关注的问题……””但这个结论有一个前提……”
- 明确判断的适用边界：在什么条件下成立、什么情况下还不确定
- 不要假装客观中立地列事实；要有主线判断

### 避免的句式

- ❌ **”不是 X，而是 Y”**——即使只出现一次也尽量不用。改写时的核心思路：直接陈述你认为对的那个，让它的重量自然压过另一个，不需要先否定再拔高。
  - ❌ “不是 A/B 方案更好，而是 C 才是方向”
  - ✅ “C 才是主线，A/B 是过渡方案”
  - ✅ “C 出现之后，A/B 的讨论变得次要”
  - ✅ “A 的问题在于 X；C 直接绕开了这个约束”
- ❌ **”不难发现……” / “可以看出……” / “由此可见……”**——宣告自己在分析。把结论直接写出来，不需要提前点名。
- ❌ **”值得注意的是……”**——同上，开头直接说结论。
- ❌ **”在 X 快速发展的今天……” / “随着 X 的不断演进……”**——无信息量的时间状语开头，直接切入具体事实。
- ❌ **”当然，这也带来了新的挑战……”**——假装平衡的套话转折。如果真有值得讨论的局限，说清楚是什么局限。
- ❌ **”综上所述，我们可以得出……”**——结论段直接写结论，不要过渡公式。
- ❌ 每个 PR / 每个模块单独一段流水账，失去全文贯穿的主线
- ❌ “X 作为 Y 领域的重要 Z……”——空洞的重要性声明，改用具体事实或数字说话

### 丰富语言表达

同一位作者在同一篇文章里，高频词和重复句式会让文章听起来像模板。写完检查以下几点：

**高频词分散**：同一段落内避免重复相同的词，尤其是”这意味着””核心””说明””值得注意的是”等词。改用同义表达：
- “这意味着” → “换言之””由此可见””这带来的结果是”
- “核心” → “关键””本质上””主线是”
- “说明” → “指向””表明””反映”

**句式多样性**：
- 判断句（”X 是 Y”）之后接叙述句（”具体而言……”）或对比句（”但 Z 出现了……”），不要连续三句以上都是相同的”X 是 Y”主系表结构
- 过渡句不要每次都用”这”开头，换用”而””但””同时””此外”等连接词引导下一层意思

**段内节奏**：每段至少有一句不是以”X 的 Y 是 Z”的形式开头，适当使用短句打破长句的沉闷感。

**检查方法**：写完后大声朗读一遍，舌头打结的地方通常是表达最机械的地方，需要重写。

### AI 味的深层来源

单个句式手动改掉还不够，AI 写作的气味往往来自更底层的行文习惯。写完后做一次快速扫描：

**对称结构过密**：AI 倾向于生成高度对称的并列结构——三点并列、四点并列、每点字数相近——读起来整齐但机械。最重要的点值得写三倍内容，其他的一句带过。强制均分篇幅本身就是 AI 味。

**把技术解释混进分析**：文章的读者是 AI Infra 工程师，不需要解释什么是 KV cache 或 CUDA kernel。如果一段话的主要内容是背景知识铺垫，要么删掉，要么一句话带过直接去讲判断。

**每段解读自己刚写的内容**："这意味着……""这说明……""这表明……"——如果事实和机制已经说清楚，结论不需要被再解读一遍。把结论前置成开篇判断，或者让读者自己得出。

**形容词替代数字**：说"吞吐量提升 3.2 倍"，不说"大幅提升吞吐量"；说"延迟从 120ms 降到 45ms"，不说"显著降低延迟"。在 AI Infra 写作里，数字是最好的修辞，具体数字本身就传达态度。

**连续以"这"开头**：连续三段以上段首是"这一设计""这种做法""这意味着"，强制换词，或重构段落让主语有变化。

### 标题编号

- H2 用中文数字顿号：`## 一、` `## 二、` `## 三、`
- H3 可用阿拉伯数字：`### 1.1` `### 1.2`
- 正文不用 H1（`#`），front matter 的 `title` 会自动渲染成页面 H1

## 第五步：格式规则

**根据文章类型，读取对应的格式规范文件：**

- **Brief** -> 读 `references/brief-format.md`（frontmatter 模板、引用格式、完整结构模板）
- **Essay** -> 读 `references/essay-format.md`（frontmatter 模板、引用格式、完整结构模板）
- **Reading** -> 读 `references/essay-format.md`（格式与 Essay 完全一致；注意 `kind: reading`、`category: Reading`、`author: Ethan`）
- **如果参考资料含有可用图片** -> 再读 `references/image-handling.md`（候选图筛选、原图抓取、失败回退、落盘命名）
- **如果用户要求微信公众号版本** -> 再读 `references/wechat-format.md`（公众号改写规则、参考资料链接保留、输出路径）
- **如果用户要求的是 essay 的微信公众号技术长文** -> 把它当成独立长文路径处理，不要沿用 brief 的默认配图与配色假设

这两个文件包含所有格式细节，包括完整模板。**写作前必须先读对应文件。**

## 第六步：处理图片

- Brief 和 Essay 都可以插图，但必须克制选择：
  - Brief：通常 0-2 张；只有在它能明显解释当天最重要的一条或两条更新时才插。
  - Essay：通常 1-4 张；优先选择架构图、方法流程图、关键实验图。
- 按 `references/image-handling.md` 的顺序优先尝试抓取原图：
  - repo / GitHub：优先 raw 文件、user-attachments、README 中的原始资源链接
  - blog：优先正文 figure / picture / srcset 中的最大可用原图
  - paper：优先 arXiv HTML 中的 figure 原图，其次其他官方 HTML 版本，最后才考虑 PDF 裁图
- 图片下载后保存在 `/assets/{post-slug}/`，命名尽量稳定：
  - `fig-1-architecture.png`
  - `fig-2-benchmark-throughput.webp`
- 在正文对应位置插入：
  - `![描述](/assets/{post-slug}/fig-1-architecture.png)`
  - `*图 1：这张图说明了什么；必要时在句末补充来源。*`
- 如果源站阻止抓取或图片链接失效，执行回退策略；若多次尝试后仍不可得，就跳过该图，并在正文用文字把关键结论讲清楚。

---

## 第七步：内容标签

写完正文、完成图片处理后，给文章打标签：

1. **读取 `references/content-tags.md`**，获取当前标签体系和选标签规则。
2. 阅读文章正文，识别主要技术主题（通常 2–4 个）。
3. 从体系表中选 2–5 个匹配标签，写入 front matter：`tags: [Tag1, Tag2, Tag3]`。
4. 框架专属标签（vLLM / SGLang / TRT-LLM / llama.cpp / Mooncake）只在该框架是文章主要分析对象时才加。
5. 如果现有标签无法覆盖，先用最接近的标签，然后在说明中提示用户可能需要新增。

- GitHub.io 默认保存路径：`/Users/lychee/mycode/miraclefarms.github.io/_posts/YYYY-MM-DD-slug.md`
- GitHub.io 文件名：日期取自 front matter 的 date 字段 + 英文 slug（小写、连字符分隔）
  - 例：`2026-04-15-vllm-paged-attention-design.md`
  - 例：`2026-04-15-ai-infra-daily-brief-speculative-decoding.md`
- 如果用户要求微信公众号版本，保存到：`/Users/lychee/mycode/miraclefarms.github.io/docs/wechat/YYYY-MM-DD-slug-wechat.md`
- `essay -> 微信公众号技术长文` 时，文件 front matter 里额外写入 `wechat_variant: essay-longform`，让发布链路明确选择技术长文主题与图片处理策略
- 如果用户同时要求两个渠道，先完成 GitHub.io 版本，再基于同一判断改写出微信公众号版本
- **不要主动 commit 或 push**，除非用户明确要求

## 快速检查清单

写完后自检：

- [ ] front matter 所有必填字段都有？
- [ ] `kind` 和 `category` 配对正确？（essay/Essay、reading/Reading、brief/Brief）
- [ ] Essay 作者是 `Lychee & Ethan`？Reading 作者是 `Ethan`？Brief 作者是 `荔枝不耐思`？
- [ ] 日期用 `+0800`？
- [ ] Brief：引用是 `[[N]](url)` 格式？有 `## 参考来源` 章节？
- [ ] Essay：正文引用是 `<a href="url">[N]</a>`；文末有 `## 参考资料`，且每条参考资料是 `[N] [Title](url)`，页面不直接展示裸 URL？
- [ ] 标题用了全角竖线 `｜`（Brief）或无竖线（Essay）？
- [ ] H2 用了中文数字编号？
- [ ] 开篇是判断，不是背景介绍？
- [ ] 没有满篇 bullet list，是连续叙述？
- [ ] 没有出现"不是 X，而是 Y"、"值得注意的是"、"不难发现"、"随着 X 的不断演进"、"综上所述"、"X 作为 Y 领域的重要 Z"等 AI 味句式？
- [ ] 开篇第一句是判断或具体场景/数字，不是抽象的重要性声明？
- [ ] 至少有 2 处用具体数字锚定判断（成本、性能、倍数、百分比）？
- [ ] 每个主要技术段落结尾都有"so what"——说清了这对读者意味着什么？
- [ ] Brief 的每个 H2 章节有 1-2 处 bold 标记核心判断句？
- [ ] 全文至少切换了 2 种视角（拆解者/翻译者/连线者/质疑者/考古者）？
- [ ] 没有连续三段以上以"这"开头？没有纯背景铺垫的段落？评价用数字而非形容词？
- [ ] 如果参考资料里有高价值图片，是否已经尝试抓取并只插入最相关的 0-4 张？
- [ ] 图片是否放在对应分析段落附近，而不是文末堆图？
- [ ] 图片路径是否位于 `/assets/{post-slug}/`，图注是否说明“这张图说明了什么”？
- [ ] 如果输出微信公众号版本，正文主体里是否没有 Markdown 链接或 HTML 链接，并且 URL 只出现在参考资料括号中？
- [ ] 如果输出微信公众号版本，是否已经按 `references/wechat-format.md` 改写成适合公众号阅读的版本？
- [ ] 如果输出的是 essay 的微信公众号技术长文，是否已经写入 `wechat_variant: essay-longform`？
- [ ] 如果输出的是 essay 的微信公众号技术长文，是否保留了与 GitHub.io essay 相同的正文配图，而不光是题图？
- [ ] 如果输出的是 essay 的微信公众号技术长文，是否明确走经典蓝主题，而不是 brief 的默认绿色主题？
- [ ] front matter 里有 `tags` 字段？标签数量在 2–5 个之间？大小写与 `references/content-tags.md` 体系一致？
- [ ] 框架专属标签（vLLM / SGLang 等）只在该框架是主要分析对象时才出现？
